1. 문제와 대상

운영진과 회원은 여러 나라의 미술관을 방문객 수와 국가 조건으로 비교한다. 목록을 직접 찾아야 하는 부담을 줄이기 위해 조건에 맞는 후보를 먼저 보여 주고, 후보 안에서 AI가 한 곳을 제안하도록 했다.

3. 탐색 — 그림 두 장

분포의 중심1–2백만 구간이 29곳으로 가장 많다.
합계 검증구간 합계 72곳은 정제 행 수와 일치한다.
해석 주의Vatican·Brazil처럼 n=1인 국가의 평균은 일반화하지 않는다.

쓰임 국가 평균은 규모 비교용 참고값이며, 개별 추천은 후보별 실제 방문객 수와 국가 데이터를 사용한다. Wikipedia 한 페이지의 72곳이므로 전체 미술관 분포로 일반화하지 않는다.

4. 해결 방식과 AI 적용점

구분적용 내용
필터국가와 최소 방문객 수로 후보를 거르고, 후보 0개면 AI를 호출하지 않는다.
AI 범위최대 5개 후보의 이름·방문객 수·국가만 전달한다. 후보 밖 이름, 새 숫자, 표에 없는 정보는 금지한다.
결정 규칙후보 중 방문객 수가 가장 적어 조건 경계에 가까운 곳부터 판단하도록 지침을 제한한다.
검증·보안서버가 추천 후보의 이름·방문객 수·국가를 data/data.json과 다시 대조하고, API 키는 Vercel 환경변수로 관리한다.
실패 처리입력 오류·후보 0개·API 한도·상위 API 오류를 구분해 안내하며, 후보 밖 결과는 카드에 반영하지 않는다.

5. 구현 결과와 운영 판단

  • 필터, 후보 카드, 후보 없음 안내는 배포 주소에서 동작한다.
  • 정상·후보 1개·후보 없음 조건에서 후보 수와 데이터 값은 일치했다.
  • Gemini 무료 API 한도 도달 시 사용자 안내가 표시된다.
  • 추천 결과가 후보 목록 밖이거나 원본 데이터와 맞지 않으면 카드에 반영하지 않는다.
  • 결재 판단: 조건부 승인. 추천 지속 성공률과 비용은 운영 관찰이 필요하다.

6. 측정과 사용자 확인

  • apply_filter, get_recommendation, select_item 이벤트를 구성했다.
  • GTM 미리보기에서 태그 실행, GA4 DebugView에서 select_item 1회 도착을 확인했다.
  • M18 짝 테스트에서 조건 적용 → 추천 요청 → 결과 확인 순서로 과제를 끝냈다.
  • M19에서 음수·잘못된 방문객 수 입력을 전용 안내로 처리했다.
  • select_item 1회는 도착 증거이지 회원 전체의 전환율은 아니다.

7. 한계와 다음 단계

  • Wikipedia 한 페이지 72개라 최신성과 전체 대표성이 제한된다.
  • 무료 API 한도와 호출 비용을 아직 수치로 확인하지 않았다.
  • 짝 1명과 내 재검사만으로 모든 회원의 사용성을 판단할 수 없다.
  • 한 달 동안 추천 성공·한도·오류와 select_item 비율을 관찰한다.
  • 2~3명의 추가 회원에게 같은 과제를 주고 모바일 차이와 멈춘 화면을 기록한다.
